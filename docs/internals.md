# rdn-fcode

An Open Firmware FCode driver for Juniper Radeons (HD 5750/5770/6750/6770,
DCE4) in a Power Mac G5. It POSTs the card through its own AtomBIOS, reads the
display's EDID, and sets a mode on a DVI or HDMI port. Everything is written
in Forth, ported from Linux's radeon driver by way of
[RadeonNI](reference/repo/RadeonNI-OSX).

## Layout

| Path | What |
|---|---|
| `src/atom.fs` | AtomBIOS command-table interpreter (port of Linux `atom.c`) |
| `src/consts.fs` | Registers, table ids and struct offsets, generated by `tools/gen-consts.c` |
| `src/card.fs` | Register access, logging, POST (`card-post`) |
| `src/i2c.fs` | Bit-banged DDC, EDID reading, detailed-timing parsing |
| `src/modeset.fs` | Board outputs from the object table, PLL, mode set, `display-start` |
| `src/platform.fs` | Open Firmware side: PCI config, BARs and `reg`, register access, delays, VBIOS copy from the ROM |
| `src/probe.fs` | The card node: probe, POST, mode, EDIDs of all outputs, a child node per output |
| `src/display-node.fs` | The display child of the driven output: properties, `open`/`close`, colours, rectangles |
| `rom/rdn.fth` | Top-level FCode file; `toke rom/rdn.fth` writes `rom/rdn.fc` |
| `tools/mkrom.py` | Builds a flash image: the card's dump plus the FCode as an Open Firmware image |
| `tools/checkrom.py` | Checks a flash image, and compares it with the dump and the FCode |
| `test/` | Host tests under gforth (see below) |
| `reference/` | The Visiontek 6770 VBIOS, Linux sources, the RadeonNI repo, AMD docs |

The card code needs a few words from the platform: `u32 reg@ reg! ioreg@
ioreg! pll@ pll! mc@ mc! atom-us atom-ms@ atom-warn rom`. `src/platform.fs`
supplies them in Open Firmware, and `test/prelude.fs` in gforth.

## The device tree

Laid out like Apple's Mac Radeon ROMs, where `ATY,PrionaceParent` has a node per head (`ATY,Prionace_A`, `_B`):

- **The card node** is `ATY,JuniperParent`, after the chip's code name.
- **Its children** are the card's three heads, `ATY,Phantom_A@0`, `_B@1` and `_C@2`, with the head number as the unit address. They always exist, connected or not.

It's a Mac card that never existed, so no ATI NDRV or Mac OS X driver matches these names.

```
/pci@0/ATY,JuniperParent@10   the card: reg, #address-cells 1, #size-cells 0,
                              open, close, decode-unit, encode-unit, rdn-decode
  ATY,Phantom_A@0       DVI-I (UNIPHY1 A, DDC 93)            <- console here
  ATY,Phantom_B@1       DVI-I (UNIPHY0 A, DDC 92)
                        alt: HDMI (UNIPHY2 B, DDC 90)
  ATY,Phantom_C@2       DisplayPort (UNIPHY2 A, DDC 91)      stub until AUX
```

The heads are assigned from the ROM's connector list, so another board's layout works too:

- A and B are the first two DVI connectors.
- HDMI is B's alternate connector, or a head of its own on a board with fewer DVI ports.
- C is DisplayPort.

The console is the head holding the output that was driven.

Every head has:

- `reg` and `rdn,head`: the head number, 0, 1 or 2 (the unit address);
- `display-type`: `LCD` (digital EDID), `CRT` (analog) or `NONE`;
- `EDID` and `rdn,edid-output`, if a display answered on one of its connectors (the main one first);
- the main connector's wiring: `rdn,output`, `rdn,connector`, `rdn,connector-id`, `rdn,uniphy`, `rdn,link`, `rdn,dig` and `rdn,ddc-line`;
- if it has a second connector, the same wiring as `rdn,alt-...`.

DisplayPort connectors have no EDID yet (that needs AUX).

The driven output's child is the display. It has `device_type display`, `character-set`, `width`, `height`, `depth` (8), `linebytes` and `address`, and the methods:

- `open`, `write`, `draw-logo` and `restore` from `is-install`, and `close` from `is-remove`, as in Apple's and NVIDIA's ROMs;
- `color!`, `color@`, `set-colors`, `get-colors`, `dimensions`, and fill, draw and read rectangle, for Apple's boot screen.

`open` turns memory decode on, and the last `close` turns it off, both through the card node's `rdn-decode`. Mac OS X hangs at boot on a card left decoding (RadeonNI found this on the G5).

At probe time `rdn-probe`, in the card node:

1. publishes `reg` from the BAR sizes;
2. maps the registers and copies the x86 image (the AtomBIOS tables) out of the expansion ROM;
3. POSTs the card if needed, reads the EDIDs, sets the mode at 8 bpp and makes the children;
4. names the card node `ATY,JuniperParent` and deletes any `device_type` the firmware gave it, so the console finds the child;
5. leaves the PCI command register and ROM BAR as it found them, since the firmware may still be reading the FCode out of the ROM.

`rom/rdn.fth` then makes the display child with `new-device`, so its methods compile into it. The child clears the screen to white and loads the Mac OS default palette.

Register access is `l@ lbflip` / `lbflip l!` on the `map-in` address, the method RadeonNI used on the G5. Delays use the firmware's `us` if it has one, or else a loop timed against `get-msecs`.

## Building a flash image

```
cd rom && toke rdn.fth && cd ..
python3 tools/mkrom.py card.rom rom/rdn.fc rdn-card.rom
python3 tools/checkrom.py rdn-card.rom card.rom rom/rdn.fc
```

`card.rom` is a full dump of the card's flash chip. The builder:

- puts the Open Firmware image straight after the last image in the chain, laid out as in Apple's Mac Radeon ROMs: `55 AA`, an FCode pointer of 0x40 at offset 2, the PCI data structure at 0x20 with the card's own vendor, device and class, and the FCode at 0x40;
- clears the x86 image's last-image flag and corrects its AtomBIOS checksum byte at 0x21;
- writes only into erased (0xFF) flash, so other data in the chip is kept. The Visiontek dump, for one, has an `MCuC` block at 0x1A000. If the image won't fit, the builder stops.

The checker re-reads everything from the output. It checks that only the expected bytes differ from the dump, and that `detok` reads the FCode through to its end.

With the Visiontek dump, the FCode image lands at 0x10000–0x14000 of the 128 KB chip.

## In the emulator (qemu-g5)

Branch `radeon-juniper` of `~/qemu-g5` adds `-device radeon-juniper`, a model of the HD 6770 at its real PCI ID, 1002:68BA (`hw/display/radeon_juniper.c`). It has:

- the BARs and the expansion ROM;
- a register file with the memory-training status bits POST waits for;
- DDC with an EDID on one line (`ddc-line=`, default 3, the first DVI port);
- the LUT, and scanout of CRTC 0's surface into the QEMU window.

```
sh tools/qemu-run.sh            # stops at the Open Firmware prompt
sh tools/qemu-run.sh -- -drive file=Tiger.img,format=raw,if=ide,index=0,media=disk -boot c
```

This boots the real flash image, `out/rdn-visiontek6770.rom` (x86 image first, FCode second). In the emulator the driver:

1. cold-POSTs the card through the Visiontek AtomBIOS;
2. reads the EDID on the DVI port;
3. sets 1280×800;
4. becomes OpenBIOS's console.

OpenBIOS names the node `pci1002,68ba` and the driver renames it `ATY,JuniperParent`, with its `ATY,Phantom_x` children; there's no `model` or `compatible` for other ATI drivers to match (`out/qemu-openbios-console.png`). QEMU uses `build-juniper/`, so your own `build/` is untouched.

It needs OpenBIOS with `tools/openbios-juniper.patch` applied. It applies cleanly to `~/cat7-openbios` and makes two changes:

- It adds the Juniper IDs (68B8, 68BA, 68BE, 68BF) to the display cards OpenBIOS drives.
- It walks the whole option ROM image chain for the Open Firmware image. Stock OpenBIOS looks only at the first image.

A build of it is in `~/cat7-openbios-68ba/obj-ppc/openbios-qemu.elf`: a copy of your tree with your uncommitted changes plus this patch, built with the tree's Docker builder.

Do not use the model's `x-device-id` for tests: another ID makes Mac OS X match that card's drivers. `tools/mkrom.py --fcode-first` (FCode image first, for a stock OpenBIOS) is likewise only a fallback.

Running under OpenBIOS also fixed three things in the driver:

- It falls back to byte config accesses when the parent has no `config-l@`.
- It maps the ROM with the enable bit clear.
- It leaves the PCI command register and ROM BAR as it found them, since firmware may still be reading the FCode out of the ROM.

For Radeon-NG on this card: RadeonNI's kext matches only Turks IDs in `IOPCIMatch`, so it needs `0x68ba1002` added.

## Leopard in the emulator

```
sh tools/qemu-leopard.sh
```

This boots `~/Disks/Leopard.qcow2` on the emulated 8-core G5 with the emulated card, with `auto-boot?` on. `SNAPSHOT=1` writes nothing to the disk.

- **Without a kext,** Leopard reaches the desktop on the FCode's framebuffer: 1280×800 at 8 bpp (`out/qemu-leopard-desktop-8bpp.png`).
- **With RadeonNI ported to the Juniper** (`~/RadeonNI-OSX`, branch `juniper`, see its `docs/JUNIPER.md`), the kext loads on the emulated HD 6770. It reads the VBIOS from the card's ROM, sets 1280×800 at 32 bpp and takes the console over (`out/qemu-leopard-radeonni-desktop.png`, `out/qemu-leopard-radeonni-log.png`).

`out/RadeonNI-10.5.iso` is attached as a CD (volume `RADEONNI`). It holds the ported kext built with `make LEOPARD=1` in a Tiger guest with Xcode 2.5, plus RadeonNI's `install.sh`, `uninstall.sh`, `README.txt` and `LEOPARD`. In Leopard's Terminal:

```
sudo sh /Volumes/RADEONNI/install.sh --check
sudo sh /Volumes/RADEONNI/install.sh
```

then restart.

**A tested disk with the kext already in:** `build/leopard-overlay.qcow2` is a qcow2 overlay on top of `~/Disks/Leopard.qcow2` with RadeonNI installed. Boot it with:

```
DISK=build/leopard-overlay.qcow2 sh tools/qemu-leopard.sh
```

An overlay is only valid while its base image is unchanged. Once you boot `Leopard.qcow2` itself, delete the overlay and make a new one with `qemu-img create -f qcow2 -F qcow2 -b ~/Disks/Leopard.qcow2 build/leopard-overlay.qcow2`.

The OpenBIOS for all of this needs `tools/openbios-juniper.patch`. It does three things:

- lists the card's expansion ROM in `assigned-addresses`, because Mac OS X clears a ROM BAR that isn't listed there and the kext then can't read its VBIOS;
- adds the Juniper IDs;
- finds an FCode image after the x86 one.

A build of it is in `~/cat7-openbios-68ba`.

How the kext is built: a scratch disk (`build/kextbuild2/build.dmg`) holds RadeonNI's `hw/` and `kext/` and `build.sh`. A Tiger guest booted from `~/Disks/Tiger.img` with `snapshot=on` (nothing written to it) runs `sh /Volumes/RDNBUILD/build.sh`. `tools/make-iso.sh` turns the package into the ISO.

Two caveats from these runs:

- **Single-user mode, emulator only:** with this QEMU branch, Leopard's ATA disk can report "media is not present" in single-user mode and the kernel panics. It hasn't happened in normal boots. The kext on the overlay was installed in single-user mode with 1 CPU.
- **The QEMU card model** has no vblank interrupt or hardware cursor yet. The kext runs without them (software cursor).

## Trying it without flashing

The driver reads the AtomBIOS tables from the card's own ROM, so it also
runs on a stock card. From the Open Firmware prompt (telnet, or another card
as the screen), with `rdn.fc` copied to an HFS+ volume:

```
load hd:,\rdn.fc
dev /ht@0,f2000000/pci@.../pci1002,....    \ the card's node: show-devs
load-base 1 byte-load
.properties
" /ht@.../pci1002,...." output
```

The node path is a placeholder: find the real one with `show-devs`. Messages
from the probe start with `rdn:`. If something hangs, `reset-all` is the way
out.

These steps are untested leads from forum posts (via RadeonNI's notes). The
open question is whether `byte-load` in an existing node gives the FCode the
card's `my-space`. If not, the standard form makes a fresh child of the
bridge: `0 0 " 0" " /ht@.../pci@..." begin-package load-base 1 byte-load
end-package`, where `" 0"` is the card's unit address.

## Tests

```
sh test/run.sh
```

1. **Interpreter:** `ASIC_Init` through the Forth interpreter and through Linux's `atom.c`, on the same fake register file. The register traces must match line for line.
2. **PLL:** the divider search against RadeonNI's C version, 11,680 cases.
3. **DDC/EDID:** reads an EDID through a simulated EDID chip on the GPIO pins (`test/i2csim.fs`), including bad checksums and no display.
4. **display-start:** POST check, output discovery, EDID and a 1080p mode set, compared with `test/golden/display.txt`. Set `debug-tables?` to log every command-table call with its parameters (useful on the real card too).
5. **Display node:** the probe and every method, with Open Firmware simulated by `test/of-stub.fs`. Covers the `reg` property, the VBIOS search with x86-first and FCode-first ROM layouts, register byte order, delays, `open`/`close` and decode, the palette and LUT, and the rectangles. Compared with `test/golden/node.txt`.
6. **FCode:** `rom/rdn.fth` goes through `toke` (16 KB of FCode), so only FCode words are used.
7. **ROM image:** `test/rom.sh` builds from the Visiontek dump and checks the result. It runs the driver's own VBIOS search on the built image, and makes sure the builder refuses data in the way, a second Open Firmware image and a broken FCode file, and that the checker catches corruption.

The tests need gforth, cc and toke (fcode-utils).

## What is left out

- DisplayPort (AUX and link training): DP connectors are skipped.
- HDMI infoframes and audio: HDMI ports are driven in DVI mode.
- Display watermarks: CRTC 0 gets the whole line buffer, with no priority marks.
- Spread spectrum on the display PLL: left as `ASIC_Init` set it.
